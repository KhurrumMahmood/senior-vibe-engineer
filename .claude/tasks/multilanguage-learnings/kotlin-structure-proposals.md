# Kotlin/JVM accepted structure proposals

`propose-boundary` and `propose-folder-reorganization` consume accepted
Kotlin evidence rather than rerunning detection. The boundary branch binds one
explicit `find-omnibus` domain to every fully rendered qualified declaration,
signature, direct resolved caller, source block, new file, package decision,
and lexical/semantic manifest addition. The folder branch binds one accepted
`find-folder-topology-drift` cluster to every selected file, declaration,
direct caller, same-package move, and lexical/semantic manifest replacement.

Both branches require the current complete `map-subsystem` artifact and a
content-addressed human acceptance. They refuse unless overload ambiguity,
reflection and callable references, delegation, generated/KAPT/KSP and plugin
sources, Gradle variants, Java and external callers, runtime dispatch and
equivalence, and JVM ABI are explicitly absent or retained as separate
approval boundaries. The deprecated K1 compiler facts remain pinned to the
exact Kotlin 2.4.10 compiler and stdlib jars; they are not the stable Analysis
API and do not create runtime or mutation authority.

The final output is always exactly `proposal.md`, `evidence.json`, and
`scope.json`. An accepted run executes the exact manifest-selected native test
and smoke with Kotlin/JVM 2.4.10 and JDK 17 on the current tree, applies the
accepted plan only in a disposable copy, repeats the same native proof there,
and verifies the host source census is unchanged. A copied closure consists of
the selected proposal skill plus `_kotlin-semantic/kotlin_structure_proposals.py`;
it imports no detector, map producer, repository script, build system, or
network service.

The focused fixture proves a three-declaration boundary extraction and a
four-file same-package folder plan through current, disposable, independent,
copied, refusal, and exact replacement paths. This does not prove arbitrary
Gradle builds, package changes, generated inputs, Java interoperability,
Android or Multiplatform layouts, framework registration, behavioral
equivalence, runtime reachability, JVM ABI compatibility, or refactor safety
outside the accepted fixture.
